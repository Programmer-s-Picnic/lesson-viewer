Day 1 · Mon, 16 Nov 2026Teaching

Run HTTP and HTTPS Servers — Localhost, Wi-Fi & Chrome Network

Learning objective: Start HTTP on localhost and Wi-Fi, inspect requests in Chrome DevTools, then create a local TLS certificate, run HTTPS on port 8443 and compare both protocols.

90-minute practical-first sequence

  1. 0–10 minRun the HTTP server on localhost:8000
  2. 10–20 minOpen the HTTP site on a phone through Wi-Fi
  3. 20–30 minInspect HTTP GET in Chrome Network
  4. 30–40 minUnderstand HTTPS, TLS, certificates and trust
  5. 40–60 minGenerate certificate and run HTTPS:8443
  6. 60–75 minInspect HTTPS using Chrome Network and Security
  7. 75–85 minCreate index.html and compare HTTP/HTTPS
  8. 85–90 minAnswer questions, stop servers and clean up

Instructor opening script (begin with action, not theory)

Welcome to the AWS course. Before defining the word “server”, we will run one. Open Command Prompt.
We will first view our server from the SAME computer using localhost. Then we will open exactly the same website on a PHONE through Wi-Fi.
Finally, we will inspect HTTP and HTTPS in Chrome Network and explain what TLS does.
Today's question: how can the same laptop serve both protocols, and why does the browser warn about a self-signed certificate?

Step 1 — Run HTTP on localhost (0–10 minutes)

Open Command Prompt on a Windows computer with Python. Make an aws-day1 folder and a site subfolder. We will serve only the site/ folder, keeping certificates and private keys outside the web document root.

Windows Command Prompt — first command
mkdir aws-day1
cd aws-day1
mkdir site
py -m http.server 8000 --bind 127.0.0.1

If py is not available but Python is installed, use python -m http.server 8000 --bind 127.0.0.1 --directory site. Leave the terminal open. Open Chrome on this computer and visit http://localhost:8000/ (or http://127.0.0.1:8000/). The directory listing demonstrates that a server is already answering requests.

Ask: Does Chrome display a local file URL (file://) or an HTTP URL? Why is a process listening on port 8000?

Step 2 — Run HTTP over Wi-Fi (10–20 minutes)

First stop the localhost-only server with Ctrl+C. In another Command Prompt window, run ipconfig and find the IPv4 Address under the active Wi-Fi adapter. Do not use the Default Gateway: that commonly belongs to the router.

Find your Windows computer's Wi-Fi address
ipconfig

# Example ONLY:
# IPv4 Address   : 192.168.1.5   ← laptop
# Default Gateway: 192.168.1.1   ← router, NOT the website

Return to the website folder and restart Python, now listening on all IPv4 interfaces. Use this only on a trusted classroom or home network.

Restart server for LAN/Wi-Fi access
py -m http.server 8000 --bind 0.0.0.0 --directory site
# Or: python -m http.server 8000 --bind 0.0.0.0 --directory site

On the phone connected to the same Wi-Fi, open Chrome and enter http://192.168.1.5:8000/, replacing 192.168.1.5 with the laptop's actual Wi-Fi IPv4 address. Keep the Python server terminal open and watch the GET request appear in its output.

If the phone says “connection refused”

  • Check whether the laptop opens http://localhost:8000 first.
  • Confirm the Python server is still running and bound to 0.0.0.0, not 127.0.0.1.
  • Use the laptop Wi-Fi IPv4 address, NOT the Default Gateway (router) and NOT localhost on the phone.
  • Check that the phone and computer are on the same LAN; guest Wi-Fi, VPNs or access-point client isolation can interfere.
  • If Windows Firewall blocks TCP port 8000, allow access for the trusted Private network only; avoid exposing it on Public networks.
  • Use http://, not https://. The basic Python demonstration server does not provide HTTPS.

Step 3 — Inspect HTTP in Chrome Network (20–30 minutes)

  1. On the Windows computer, open http://localhost:8000/ in Google Chrome.
  2. Press F12 (or Ctrl+Shift+I), select the Network tab, and choose All or Doc.
  3. Keep the Network tab open and reload the page (Ctrl+R).
  4. Click the document request (usually localhost or /). In Headers, find Request URL, Request Method GET, Status Code (normally 200) and Response Headers.
  5. Open Response to inspect returned HTML or the directory listing. Compare with what Chrome renders in the browser.
  6. Open the website again on the phone; the Python terminal should log its GET request. Chrome on Android does not ordinarily expose desktop DevTools, so use the Windows Chrome Network panel for detailed inspection.

What students should observe in DevTools

Request URL
http://localhost:8000/ on the Windows browser (or the LAN IPv4 address if tested from Windows).
Request Method
GET: the browser requests a resource.
Status Code
200 OK when the server returned the page successfully; other requests such as favicon may have different statuses.
Remote Address
The endpoint/port used for this connection, as displayed by Chrome.
Response
HTML content or a directory listing returned by the server.
Timing
The time Chrome records for phases of the request.

Step 4 — Explain HTTPS, TLS and certificates (30–40 minutes)

HTTP sends requests and responses without transport encryption. HTTPS is HTTP protected by TLS (Transport Layer Security). TLS encrypts data in transit and helps prevent tampering. A trusted certificate also helps a browser authenticate the server. We will create a self-signed certificate for local learning: the connection can be encrypted, but Chrome and Android will not automatically trust the certificate.

What will students compare?

  • http://localhost:8000/ — HTTP, no TLS encryption
  • https://localhost:8443/ — HTTPS, TLS encryption with an untrusted local certificate
  • http://LAPTOP_IP:8000/ and https://LAPTOP_IP:8443/ — same website accessed over Wi-Fi on separate ports

Step 5 — Create and run the local HTTPS server (40–60 minutes)

First, download two Python files from the AWS HTTPS demo folder: generate_cert.py and https_server.py. Place them in aws-day1/. Put the sample index.html in aws-day1/site/. Never place key.pem inside site/. Both web servers will expose only site/, protecting the private key from accidental file downloads.

Install certificate-generation library
py -m pip install cryptography
Generate a self-signed certificate for localhost and Wi-Fi
ipconfig
# Replace 192.168.1.5 with laptop's Wi-Fi IPv4 Address (not Default Gateway).
py generate_cert.py 192.168.1.5
# Creates cert.pem and key.pem beside the scripts, NOT in site/.
Start HTTPS in a SECOND Command Prompt window
cd aws-day1
py https_server.py
# HTTPS: https://localhost:8443/
# Wi-Fi: https://192.168.1.5:8443/  (use your own laptop IP)

Use python instead of py where appropriate. Keep the HTTP terminal running on port 8000, and run HTTPS separately on port 8443. The example server uses Python's ssl.SSLContext and serves only the site folder. Never share or publish key.pem. This is not a production server.

Step 6 — Test HTTPS and examine Chrome (60–75 minutes)

  1. On the laptop, open https://localhost:8443/. Chrome will warn that the self-signed certificate is not trusted. That is expected, not a connection refusal.
  2. For your own teacher-created local certificate only, examine the warning; an instructor may choose a local exception if the browser allows. Never bypass warnings on unrelated websites.
  3. From a phone on the same Wi-Fi, attempt https://192.168.1.5:8443/ with the laptop's actual Wi-Fi IP. Android also will not automatically trust this certificate. Do not install unknown root certificates or disable TLS verification globally.
  4. On desktop Chrome press F12 → Network, reload the HTTPS page if accessible and inspect Request URL, GET, Status Code, and Response. Compare the URL scheme and port to the HTTP page.
  5. Inspect Chrome's Security panel (if available). Explain that an encrypted connection and a publicly trusted identity are separate concepts.
Verify this specific self-signed cert using Python (without disabling verification)
py -c "import ssl,urllib.request; c=ssl.create_default_context(cafile='cert.pem'); print(urllib.request.urlopen('https://localhost:8443/',context=c).status)"

When HTTPS does not open

  • ERR_CONNECTION_REFUSED: HTTPS server is not running on port 8443, or access is blocked.
  • Certificate warning: HTTPS is running, but this certificate is not trusted by the browser.
  • Wrong IP: Use the laptop's Wi-Fi IPv4 Address, not the router's Default Gateway.
  • Certificate hostname mismatch: Regenerate your own local certificate if your Wi-Fi IPv4 address changes.
  • Firewall: Permit incoming 8443 on a trusted Private network if necessary; never disable the entire firewall.
  • Wrong protocol: Use http:// on 8000 and https:// on 8443.
  • Real deployments: Use an appropriate trusted certificate authority and production-grade hosting.

Step 7 — Explain the request and response (75–80 minutes)

Client
Chrome is the program asking for a web page.
Server
Python http.server listens for HTTP requests and serves files from the current directory.
localhost / 127.0.0.1
Loopback access to a service on the same machine; it is not another device's IP address.
Wi-Fi IPv4 address
The laptop's reachable address within its local network, such as 192.168.1.5.
0.0.0.0 bind
The server listens on all IPv4 interfaces; visitors still use a real reachable IP address.
Port 8000
Identifies the listening service at that network address.
HTTP
The request/response protocol observed in Chrome DevTools; this demo is not encrypted.

Draw: Chrome on laptop → Python server (localhost), and Chrome on phone → Wi-Fi/router → Python server (laptop LAN IP). Both request the same content, but use different network paths.

Step 8 — Create index.html and compare both protocols (80–85 minutes)

While the server is running, create index.html inside aws-day1/site with the code below. Reload Chrome on the laptop and the phone. Then change the heading, save, and reload both again. Observe the document request in the Network tab after every reload.

aws-day1/index.html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>My First HTTP Server</title>
</head>
<body>
  <h1>Hello from Learn With Champak!</h1>
  <p>My first website over localhost and Wi-Fi.</p>
</body>
</html>

Step 9 — Recap and close both servers (85–90 minutes)

  • Close neither Chrome nor the Python server until both devices have displayed the page.
  • Show one GET request in Chrome DevTools → Network and one request in the Python terminal.
  • Stop both HTTP and HTTPS Python servers with Ctrl+C; their respective URLs should then stop responding.
  • Do not port-forward from the router or leave the demonstration server running unattended. Revert any temporary firewall exception when finished.

Exit questions

  • Why does localhost work on the laptop but not identify the laptop from the phone?
  • What is the difference between 127.0.0.1, 0.0.0.0 and the Wi-Fi IPv4 address?
  • What does Chrome show under Request Method and Status Code?
  • What happens when the server is stopped?
  • Why is 192.168.1.1 often the wrong address to use?
Homework

Submit site/index.html, screenshots of HTTP on localhost and Wi-Fi, one Chrome Network GET inspection, and notes/screenshot about your HTTPS connection and the expected self-signed certificate warning. Never share key.pem.

Day 2 · Tue, 17 Nov 2026Teaching

How Computers Communicate

Learning objective: Explain networks, Wi-Fi, Ethernet, LANs, routers and basic client–server communication.

90-minute flow

  1. 10 minReview and opening
  2. 25 minNetwork explanations
  3. 20 minWindows demonstration
  4. 20 minRole-play activity
  5. 15 minQuestions and homework

Essential concepts

Computer network
Connected devices that exchange information.
Ethernet and Wi-Fi
Common wired and wireless ways to connect devices.
LAN
A network covering a limited area such as a classroom or house.
WAN and Internet
Larger networks interconnecting many locations; the Internet is a global network of networks.
Switch and router
A switch typically connects devices in a LAN; a router forwards traffic between networks.
Access and firewalls
A service must listen on a reachable interface, and policies/firewalls must allow the connection.

Instructor opening script

Yesterday we made one computer behave like a server, but our browser and server ran on the same machine.
Suppose we now have three computers. One belongs to a teacher and two belong to students. Can the students open the website running on the teacher's computer?
Yes, if the devices can communicate and the server permits the connection. Today we will understand networks and how requests travel between devices.

Questions to ask first

  • Does being on Wi-Fi always mean that Internet access is available?
  • What conditions must be satisfied for another device to use a server?

Live demonstration and teaching steps

  1. Draw three devices connected to a classroom router.
  2. Run ipconfig in Command Prompt and identify the active adapter, IPv4 address and default gateway.
  3. Explain the difference between a network address and a website address.
  4. Role-play three students: client, router and server. The client sends a request for a homepage; the server responds.
  5. Repeat when the server is unavailable. Discuss what changes.

Code and commands

Windows Command Prompt
ipconfig

Classroom activity and instructor guidance

Assign students to client, router and server roles. Pass a paper request labelled “Send me the homepage” and return a paper HTTP response. Then make the server unavailable and ask what the user sees.

Review / exit questions

  • What is a LAN?
  • What does a router do?
  • Does Wi-Fi require an Internet connection?
  • Why might a running server still be inaccessible?
Homework / submission

Draw your home or classroom network showing the router, connected devices and an Internet link. Do not publish actual private IP addresses.

Practice Lab 1 — Localhost, Wi-Fi & Chrome Network

Learning objective: Independently serve an HTML page on localhost and across Wi-Fi; identify a GET request in Chrome DevTools Network and demonstrate access stops when the server stops.

90-minute flow

  1. 10 minInstructor briefing
  2. 60 minIndependent localhost, Wi-Fi and Network lab
  3. 15 minTroubleshooting and verification
  4. 5 minSubmission

Verification criteria

Localhost
A working URL at http://localhost:8000 and a GET request in Chrome Network.
Wi-Fi
The same site opens on a second device using the laptop's own Wi-Fi IP.
Browser inspection
A request method, URL and status can be identified and explained.
Troubleshooting
Students distinguish server failure from wrong-IP, firewall and router problems.

Instructor opening script

Today you will repeat the entire server demonstration without copying each step from the teacher.
First, make a local HTTP server work. Next, make it accessible over Wi-Fi. Finally, provide evidence from Chrome's Network tab.
A working page is good; explaining why it works is better.

Student practical checklist

Commands for reference

Localhost-only server
py -m http.server 8000 --bind 127.0.0.1
Network-address check, then Wi-Fi server
ipconfig
# Stop previous server with Ctrl+C, then:
py -m http.server 8000 --bind 0.0.0.0

Instructor guidance

Ask the student to demonstrate browser access from two devices and explain each URL. If Wi-Fi access fails, ask them to test localhost first, inspect the correct IPv4 address, confirm the server binding, and check any Private-network firewall rule. Do not require students to disable their firewall globally. Chrome Network details should be inspected on the desktop browser.

Exit questions

  • Why can the phone not use the laptop's localhost address?
  • Which IP should the phone use: IPv4 Address or Default Gateway?
  • What does the GET request represent?
  • Why does the page fail when the server process stops?
Submission

Submit index.html, a laptop localhost screenshot, a phone Wi-Fi screenshot, a desktop Chrome Network request/response screenshot, and a short troubleshooting note. Hide private information in shared screenshots.

The Internet and IP Addresses

Learning objective: Explain LAN versus Internet, IPv4/IPv6, private/public IP addresses, and routing.

90-minute flow

  1. 15 minLAN versus Internet
  2. 15 minWhat is an IP address?
  3. 15 minIPv4, IPv6 and address scope
  4. 15 minRouters and forwarding
  5. 15 minipconfig demonstration
  6. 15 minQuestions and assignments

Essential concepts

Internet
A worldwide interconnection of networks.
IP address
A network-layer address assigned to an interface in a network context.
IPv4
A 32-bit address format, often written as four decimal numbers such as 192.168.1.10.
IPv6
A larger, 128-bit address format used alongside IPv4.
Private/public address
Private IPv4 addresses can be reused in separate networks; public addressing is used for Internet reachability.
Routing
Routers forward packets toward destinations according to routes.

Instructor opening script

We have seen computers communicating over a local network.
But the Internet connects networks across cities and countries.
Imagine sending a letter to another city. You need a destination address. Networked computers also use addresses to exchange information.
Today we will study IP addresses and how routers help traffic reach its destination.

Questions to ask first

  • Can two homes each have a laptop with 192.168.1.10?
  • Is a computer's IP address always permanent?

Live demonstration and teaching steps

  1. Draw two private networks, each containing a laptop labelled 192.168.1.10.
  2. Explain why the repeated private address does not create a global conflict.
  3. Run ipconfig in Windows and identify an IPv4 address and gateway.
  4. Discuss why a public service needs a reachable endpoint and appropriate network rules.

Code and commands

Windows Command Prompt
ipconfig

Classroom activity and instructor guidance

Follow a diagram of one packet sent from a home laptop through a local router and onward to a destination network. Emphasize that actual forwarding uses routes, not knowledge of a human-readable website name.

Review / exit questions

  • What is the difference between LAN and Internet?
  • Why can two private networks reuse the same IPv4 address?
  • What does a router do?
  • What is IPv6?
Homework / submission

Draw and label client, router, Internet and destination server. Do not publicly share sensitive network configuration.

Day 5 · Fri, 20 Nov 2026Teaching

DNS, HTTP and HTTPS

Learning objective: Trace the browser's request flow from a URL through DNS, connection, TLS, HTTP response and rendering.

90-minute flow

  1. 10 minOpening and review
  2. 20 minDNS and URLs
  3. 20 minHTTP and TLS
  4. 25 minTwo live demonstrations
  5. 15 minQuestions and homework

Essential concepts

Domain name
A human-friendly name such as example.com.
DNS
A distributed system that provides records, including IP addressing information.
URL
An address identifying a resource, including scheme, hostname and optional path.
HTTP
A protocol for requests and responses between web clients and servers.
HTTPS and TLS
HTTP carried over an encrypted TLS connection; it protects traffic in transit.
HTTP status codes
200 success, 301 redirect, 404 not found, 500 server error.

Instructor opening script

Yesterday we studied IP addresses. But when you open a website, do you usually type its numeric IP address?
No. You type a name such as example.com.
How does the computer learn where to send the request? DNS helps answer that question.
Today we follow the request from the browser address bar to the returned page.

Questions to ask first

  • Why are domain names useful?
  • What can HTTPS protect, and what can it not guarantee?

Live demonstration and teaching steps

  1. Run nslookup example.com to inspect a DNS lookup.
  2. Open https://example.com in a browser.
  3. Press F12 and open Developer Tools → Network; reload the page.
  4. Select the main document request and identify the URL, method, status and response headers.
  5. Explain the simplified stages: URL → DNS → connection/TLS → HTTP request/response → rendering.

Code and commands

Windows Command Prompt
nslookup example.com

Classroom activity and instructor guidance

Students draw six connected boxes: address entered, DNS lookup, connection established, TLS, HTTP exchange and browser render. Explain that caching or reused connections can change the real sequence.

Review / exit questions

  • What is DNS?
  • How is a URL different from a domain name?
  • What does status 404 mean?
  • Does HTTPS prove that an operator is trustworthy?
Homework / submission

Draw the lifecycle of a website request with at least six labelled steps.

What Is Cloud Computing? Introducing AWS

Learning objective: Connect local server and networking knowledge to cloud infrastructure, hosted services, AWS categories and cost considerations.

90-minute flow

  1. 15 minReview local server limitations
  2. 20 minWhat cloud computing provides
  3. 20 minExplore the AWS choices
  4. 20 minClassroom choice quiz
  5. 15 minCourse roadmap and homework

Essential concepts

Cloud computing
On-demand access to computing resources and managed services over a network.
Compute
Virtual servers, functions and containers that execute programs.
Storage
Services for retaining files, objects and other data.
Databases
Managed services for storing and querying structured data.
Networking
Addressing, routing, content delivery and controlling access to services.
Responsibility and cost
Cloud still uses physical infrastructure. Users must understand pricing, security settings and ongoing usage.

Instructor opening script

On our first day we created a website on an ordinary computer.
We then learned how clients and servers communicate, how networks and IP addresses work, and how a browser asks for a webpage.
But what if our server computer is switched off? What if thousands of users visit at once? What if we need more storage?
Cloud computing gives us ways to obtain computing, storage and managed services on demand. AWS is one platform that supplies them.

Questions to ask first

  • Does cloud computing eliminate physical computers?
  • Is hosting on AWS automatically free?
  • Who remains responsible for configuring access securely?

Live demonstration and teaching steps

  1. Show the AWS getting-started screen shared for this course.
  2. Discuss each option: Build with AI, Store files, Run a server, Build an API, Set up a database, Host a website, Automate deploys, Analyse data, Run containers and Just exploring.
  3. Ask students to choose the correct option for a static site, file storage, mobile backend, student database and Node.js server.
  4. Compare running a server on your laptop versus obtaining cloud compute on demand.
  5. Preview security and budget safeguards before any paid resource is provisioned.

Classroom activity and instructor guidance

Assign five scenarios to small groups. Each group picks an AWS starting option and justifies it. Stress that a starting option may lead to multiple possible AWS services.

Review / exit questions

  • What problem can cloud computing solve?
  • Is the cloud still physical hardware?
  • Name one cloud compute and one storage category.
  • Why must pricing and IAM be learned early?
Homework / submission

Write a one-page proposal for a cloud application: users, required features, data, and which AWS starting options appear relevant.
