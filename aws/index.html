Day 1 · Mon, 16 Nov 2026Teaching · 90 min

Day 1 — HTTP Servers, Wi-Fi, Three Computers, HTTPS & Chrome Network

Today's mission: Run web servers on three Windows computers. Store the image on Computer 1, CSS on Computer 2, and HTML on Computer 3. Load the integrated webpage in Chrome, trace all three requests, create a safe local HTTPS server, and compare HTTP with TLS.

Instructor opening — read aloud

We are going to begin by RUNNING a server, not by memorizing its definition.
Computer 1 will provide images, Computer 2 will provide styles, and Computer 3 will serve our HTML.
When the page loads, Chrome must contact three different computers. We will prove that using the Network tab.
Then we will ask a new question: if we exchange this information using HTTP, can the connection be protected using HTTPS? We will run that too.

1. Learning outcomes

  • Run a local Python HTTP server bound to 127.0.0.1, then make it accessible on a trusted Wi-Fi LAN using 0.0.0.0.
  • Distinguish a server bind address, the laptop's IPv4 address, the router gateway and a TCP port.
  • Demonstrate one HTML webpage assembled from three different machines and explain what each server contributes.
  • Use Chrome F12 → Network to find each request's URL, method, status, resource type, response headers and initiator.
  • Generate a local test certificate, run an HTTPS server on port 8443, and explain the self-signed certificate warning.
  • Use evidence to diagnose wrong IP, wrong port, server stopped, HTTP 404, certificate trust and mixed-content failures.

2. 90-minute class plan

  1. 0–10 minCreate folders; start and inspect localhost
  2. 10–30 minRun three HTTP servers across Wi-Fi
  3. 30–45 minCreate HTML, CSS and image; integrate webpage
  4. 45–60 minChrome Network inspection + deliberate failures
  5. 60–80 minSet up HTTPS with local certificate; inspect TLS
  6. 80–90 minQuick tests, questions and safe shutdown

3. What to prepare before class

  • Three computers connected to the same trusted LAN; Python 3 installed; Chrome with Developer Tools.
  • Windows Command Prompt or PowerShell, and permission for the necessary Private-network firewall rules.
  • Download the three-computer lab files to the relevant machines.
  • On Computer 3, download generate_cert.py and https_server.py and preinstall the cryptography Python package if time is short.
  • Keep generated TLS private keys outside any directory served over HTTP or HTTPS. Never port-forward these demo servers.

5. First experiment — local HTTP server on a single PC

Use Computer 3. Open Command Prompt and create the web folder. Run the server bound to loopback, then browse to http://localhost:8003/. Initially you may see an empty directory listing. Stop it with Ctrl+C before switching to LAN mode.

Computer 3 — localhost HTTP server
mkdir C:\aws-day1
cd /d C:\aws-day1
mkdir site
py -m http.server 8003 --bind 127.0.0.1 --directory site

Discuss: What does localhost refer to? Why does localhost typed on the phone NOT refer to Computer 3? Why can't a server bound to 127.0.0.1 ordinarily accept a request from another PC?

6. Find each computer's IPv4 address

Run on Computer 1, Computer 2 and Computer 3
ipconfig

Find Wireless LAN adapter Wi-Fi → IPv4 Address. Write down three addresses. Ignore disconnected adapters, VPN adapters and the router's Default Gateway when identifying the server computers. If Wi-Fi uses a guest or isolated network, clients might be prohibited from reaching each other.

7. Prepare folders and start all three HTTP servers

Keep one Command Prompt open on each machine, because closing that window or pressing Ctrl+C stops its Python server. The --directory flag limits which files Python serves; do not serve your entire user profile or drive.

COMPUTER 1 — create IMAGE server
mkdir C:\aws-day1
cd /d C:\aws-day1
mkdir images
py -m http.server 8001 --bind 0.0.0.0 --directory images
COMPUTER 2 — create CSS server
mkdir C:\aws-day1

mkdir css

COMPUTER 3 — create HTML server
cd /d C:\aws-day1

What is 0.0.0.0? It is a listen/bind address meaning all IPv4 interfaces, not a destination you should type in Chrome. Clients use the computer's real Wi-Fi IPv4 address. Windows Firewall may request permission; permit only what is needed for this trusted Private network, never disable the entire firewall.

9. Verify with commands BEFORE relying on Chrome

In a separate Command Prompt on Computer 3 (not a terminal currently running a server), test each resource. These commands request only headers. The expected HTTP status for an existing file is 200.

Computer 3 — test the three servers
curl.exe -I http://192.168.1.10:8001/logo.svg
curl.exe -I http://192.168.1.11:8002/style.css

For a connectivity failure, open PowerShell and run Test-NetConnection 192.168.1.10 -Port 8001. A refused connection differs from a 404: 404 means an HTTP server responded but the requested file was not found.

10. Chrome DevTools — prove which computer served each resource

  1. On Computer 3, press F12 or Ctrl+Shift+I in Chrome and select Network.
  2. Select Disable cache while DevTools is open so old resources do not hide new network requests; press Ctrl+R.
  3. Look for index.html, style.css and logo.svg. Use the Doc, CSS and Img filters.
  4. Click each entry → Headers; record Request URL, Request Method, Status Code and Remote Address (where shown).
  5. Inspect Response for HTML/CSS and Preview for the image. Inspect Initiator to see which HTML or CSS reference caused the request.
  6. Watch the Python terminals: each server logs the requests for its own resources.

11. Failure experiments — change one thing at a time

  1. Stop Computer 1's image server with Ctrl+C. Reload Computer 3's page. The image should fail to load but the CSS can still work. In Chrome Network, inspect the failed image request; it may show a network error rather than HTTP 404.
  2. Restart Computer 1 and confirm the image returns.
  3. Stop Computer 2's CSS server. Reload and notice the page loses styling while HTML and image may remain.
  4. Restart Computer 2. Change the CSS heading color, save, disable cache, reload and observe the new style.
  5. Request a missing image such as /does-not-exist.svg while the image server is running. This should return HTTP 404. Compare 404 with connection refused.
  6. Try the router's Default Gateway in place of the laptop IP. Explain why this is generally the wrong destination.

12. HTTPS — what changes when we protect HTTP with TLS?

HTTPS wraps HTTP communication in TLS encryption. A certificate contains names/identifiers and a public key; a browser trusts the identity only if certificate validation succeeds. Our first demo uses a self-signed certificate, which encrypts traffic but produces a browser trust warning.

PropertyHTTP demonstrationHTTPS demonstration
Schemehttp://https://
Port8003 for HTML8443 for the sample HTTPS server
Traffic encryptionNo TLSTLS encryption
CertificateNot requiredRequired
Browser trustNo certificate authenticationSelf-signed cert is not automatically trusted

Important directory layout: HTTPS script and generated certificate files stay beside site/, not inside it. Python must serve site/ only. Reuse the provided HTTPS server and certificate-generator scripts.

Computer 3 — prepare HTTPS demo (new terminal)
cd /d C:\aws-day1
py -m pip install cryptography
rem Copy generate_cert.py and https_server.py here, NOT in site/
rem Replace sample IP with Computer 3's Wi-Fi IPv4 Address:
py generate_cert.py 192.168.1.12
py https_server.py

Place the secure.html sample inside Computer 3's site/. On the laptop, open https://localhost:8443/secure.html. For a phone on the same Wi-Fi, try https://192.168.1.12:8443/secure.html using the laptop IP.

Why use secure.html rather than index.html?

Our distributed index.html loads CSS and images from HTTP URLs. When the main document is loaded over HTTPS, browsers may block or upgrade those HTTP subresources as mixed content. secure.html is self-contained with inline CSS. The separate failure itself can be shown as a bonus experiment.

Expected browser behavior: Chrome will show ERR_CERT_AUTHORITY_INVALID or an equivalent warning because the generated certificate is self-signed. This is an identity trust warning, not the same as ERR_CONNECTION_REFUSED. Proceed only on this teacher-controlled local test if the browser allows, and never bypass unrelated warnings.

Computer 3 — verify this specific test certificate securely
cd /d C:\aws-day1
py -c "import ssl,urllib.request; c=ssl.create_default_context(cafile='cert.pem'); print(urllib.request.urlopen('https://localhost:8443/secure.html',context=c).status)"
rem Expected: 200 if the HTTPS server and secure.html are working.

In Chrome F12 → Network, inspect the HTTPS request and its response. Open the Security panel (when available) to examine certificate trust. For a real website, use a trusted certificate for its domain and production-grade hosting, not Python's teaching server.

Optional instructor extension — a locally trusted certificate with mkcert

Install mkcert on a development computer you control and generate a new certificate. This is optional for Day 1; certificate warning analysis is already a successful learning outcome. If cert.pem/key.pem exist, stop the server and back them up before regenerating.

Optional — trusted cert on instructor's own Windows PC
winget install --id FiloSottile.mkcert --exact
mkcert -install
mkcert -cert-file cert.pem -key-file key.pem localhost 127.0.0.1 192.168.1.12
py https_server.py

Only that computer's browsers that trust the locally installed CA should stop warning. Android or a different computer does not automatically trust this CA. Never publish the CA private key (rootCA-key.pem) or a server private key. This is not a certificate for public production use.

Day 2 — Local Domains, Windows Hosts, DNS & Testing Three Servers

Today's mission: Keep the three servers and files exactly where they were on Day 1, but replace IP-based resource URLs with images.home.arpa, css.home.arpa and site.home.arpa. Explain which computer resolves these names and how shared local DNS differs from a hosts file.

Instructor opening — read aloud

Yesterday our webpage was assembled using three different computers. It worked, but we typed addresses like 192.168.1.10 and 192.168.1.11.
Suppose those IP addresses change, or a fourth student joins the classroom. How will everyone remember the addresses?
Today we will create local domain names. The picture will still come from Computer 1, the CSS from Computer 2, and the HTML from Computer 3.
Only the names used to find these resources will change. After that, we will check every request in Chrome Network and distinguish a local hosts file from a real DNS server.

1. Prerequisites and outcomes

  • Complete Day 1 or have three reachable servers with an image on Computer 1, CSS on Computer 2 and HTML on Computer 3.
  • Know how to find the correct Wi-Fi IPv4 addresses using ipconfig and test a URL using curl.exe -I.
  • Define IP address, hostname, domain, DNS record, port and URL.
  • Edit the Windows hosts file on the browser computer with administrator privileges.
  • Prove that a name now resolves to the same server IP and that HTML, CSS and image requests still return successful responses.
  • Explain why another phone cannot automatically use these names and how a central DNS server fixes that.
  • Recognize that an HTTPS certificate must match the hostname and be trusted separately from DNS.

2. 90-minute plan

  1. 0–10 minRecap and retest all three IP-based servers
  2. 10–25 minTeach names, domains, DNS, hosts and ports
  3. 25–40 minEdit Windows hosts on Computer 3
  4. 40–55 minVerify name resolution and test resource URLs
  5. 55–70 minRun same distributed page using domains
  6. 70–80 minChrome Network inspection and failure experiments
  7. 80–90 minShared DNS, HTTPS names, assessment

3. Required setup

  • Three Windows computers on the same trusted Wi-Fi, Python servers running as in Day 1.
  • Administrator privileges on Computer 3 for editing hosts.
  • Backup of the original hosts file; use only classroom entries you understand.
  • Chrome Developer Tools open on Computer 3, and a second device for the optional network-wide DNS test.
  • Use the same sample files from Day 1.

4. Understand the terms using one URL

http://images.home.arpa:8001/logo.svg

Part of the URLValueMeaning
Schemehttp://The browser speaks HTTP
Hostnameimages.home.arpaA name that must be resolved to an address
Address after resolution192.168.1.10 (example)Computer 1's reachable IPv4 address
Port:8001Which service to connect to on that computer
Path/logo.svgWhich file to request from the server

A hostname is not a replacement for the port. DNS resolves names to addresses; it does not generally decide which HTTP port our Python server uses. Multiple domain names can point to one IP. Browsers then use the hostname, port and path to choose the connection and resource; later we can introduce reverse proxies and virtual hosting.

5. Why use home.arpa?

home.arpa is a special-use namespace designated for names within home networks by RFC 8375. It is appropriate for our classroom's local-domain demonstration; we are not registering these domains on the public Internet. A name such as images.home.arpa has significance in the local network where it is configured.

Important distinction: hosts file ≠ DNS server

A hosts file is a local mapping on one computer. A DNS server responds to DNS queries from multiple clients. Today we first use the hosts file so we can see exactly how name-to-IP mapping works, then outline shared DNS.

6. Review: confirm the three original IP-based resources work

Do not begin debugging DNS until all three IP-based requests already work. From Computer 3, run:

Computer 3 — baseline before domain mapping

curl.exe -I http://192.168.1.10:8001/logo.svg
curl.exe -I http://192.168.1.11:8002/style.css
curl.exe -I http://192.168.1.12:8003/index.html

Expected: Status 200 for each existing resource. If a request fails already, correct the server, IP, filename or firewall first. A domain name cannot repair a server that's unreachable by IP.

7. Create names in Windows hosts (Computer 3 only)

  1. On Computer 3, open Notepad by right-clicking and choosing Run as administrator.
  2. In Notepad, select File → Open and navigate to C:\Windows\System32\drivers\etc\hosts. Choose All Files (*.*) so the file becomes visible.
  3. Back up the existing entries, and add the three mappings below at the end of the file. Replace each sample IP with the actual address of that computer.
  4. Save as hosts with no .txt extension. If Windows refuses, verify Notepad is elevated.
  5. Open a new Command Prompt and run ipconfig /flushdns.
  6. Keep the servers running throughout the test.
Windows hosts file — add on Computer 3
# Computer 1: image server
192.168.1.10   images.home.arpa

# Computer 2: CSS server
192.168.1.11   css.home.arpa

# Computer 3: HTML server
192.168.1.12   site.home.arpa
Windows Command Prompt — clear Windows DNS resolver cache
ipconfig /flushdns

Explain carefully: These mappings are used by applications on Computer 3 that use the Windows hostname-resolution mechanism. They do not update the router, register a public domain or change what DNS servers on other devices know.

8. Test the hostname mappings before editing HTML

First check name resolution, then check the actual HTTP service. The DNS/hosts mapping is not useful unless the destination server and correct port are reachable.

Computer 3 — resolve a name with Windows and test HTTP
ping -4 images.home.arpa
ping -4 css.home.arpa
ping -4 site.home.arpa

curl.exe -I http://images.home.arpa:8001/logo.svg
curl.exe -I http://css.home.arpa:8002/style.css
curl.exe -I http://site.home.arpa:8003/index.html

Expected: ping -4 displays the mapped IPv4 address when name resolution works, though ICMP replies may be blocked by firewalls. curl.exe -I should receive HTTP 200 when the server is running and the resource exists.

Teaching experiment: what does nslookup do?

Query DNS independently
nslookup images.home.arpa

Expected observation: nslookup consults DNS servers; it normally does not use hosts-file mappings. It may return no record even when ping shows the mapped IP and curl.exe can reach the host. That is not necessarily an error in the hosts file. This experiment distinguishes local hosts-based name resolution from actual DNS queries.

11. Prove that the names exist only on Computer 3

On a fourth Windows computer or an Android phone connected to the same Wi-Fi, try http://images.home.arpa:8001/logo.svg. Unless that device has its own mapping or uses a configured local DNS server, the name may fail to resolve even though http://192.168.1.10:8001/logo.svg loads.

Critical lesson: The computer running the browser must resolve the remote image/CSS hostnames. Putting entries only on the HTML server will not make the names work for all other browsers.

12. Next level: define shared domains for the whole Wi-Fi

  1. Choose a router with support for local DNS records, or a dedicated local DNS resolver (for example Pi-hole or AdGuard Home).
  2. Reserve stable LAN IPv4 addresses for the image, CSS and HTML computers using the router's DHCP address reservations.
  3. Create local A records for images.home.arpa, css.home.arpa and site.home.arpa.
  4. Configure the router's DHCP settings to advertise the local DNS resolver IP to clients, or set that resolver on the specific test devices.
  5. Renew connections where necessary; test resolution from a second Windows computer and the phone. Android Private DNS, browsers' secure-DNS settings or a VPN may bypass or alter local DNS behavior.
  6. Verify by domain-based HTTP requests. Do not expose the teaching server or local DNS service to the public Internet.

Once a real shared DNS server answers these names, nslookup images.home.arpa YOUR_DNS_SERVER_IP should return the record, unlike the earlier hosts-only experiment.

13. Optional HTTPS with a local domain

DNS resolution alone does not make HTTPS trusted. If Chrome visits https://site.home.arpa:8443/secure.html, the certificate's Subject Alternative Name must include site.home.arpa, and the client must trust the certificate's issuer. Day 1's self-signed generator produces names for localhost and a Wi-Fi IP, not site.home.arpa.

On a trusted instructor Windows machine, mkcert can generate a locally trusted certificate containing the hostname. Back up or replace the old test cert.pem and key.pem after stopping the HTTPS process.

Optional — add a trusted HTTPS certificate for the local domain
cd /d C:\aws-day1
rem Run only on a development computer you control:
mkcert -install
mkcert -cert-file cert.pem -key-file key.pem site.home.arpa localhost 127.0.0.1 192.168.1.12
py https_server.py
rem Open https://site.home.arpa:8443/secure.html

The Windows browser may trust mkcert's local CA after installation, but other computers and phones will not trust it automatically. Never distribute rootCA-key.pem or a private server key. For the classroom's distributed HTML, keep using HTTP until every referenced CSS/image resource also has a suitable HTTPS endpoint: an HTTPS webpage that loads HTTP assets can trigger mixed-content blocking or upgrading.

The Internet and IP Addresses

Learning objective: Explain LAN versus Internet, IPv4/IPv6, private/public IP addresses, and routing.

90-minute flow

  1. 15 minLAN versus Internet
  2. 15 minWhat is an IP address?
  3. 15 minIPv4, IPv6 and address scope
  4. 15 minRouters and forwarding
  5. 15 minipconfig demonstration
  6. 15 minQuestions and assignments

Essential concepts

Internet
A worldwide interconnection of networks.
IP address
A network-layer address assigned to an interface in a network context.
IPv4
A 32-bit address format, often written as four decimal numbers such as 192.168.1.10.
IPv6
A larger, 128-bit address format used alongside IPv4.
Private/public address
Private IPv4 addresses can be reused in separate networks; public addressing is used for Internet reachability.
Routing
Routers forward packets toward destinations according to routes.

Instructor opening script

We have seen computers communicating over a local network.
But the Internet connects networks across cities and countries.
Imagine sending a letter to another city. You need a destination address. Networked computers also use addresses to exchange information.
Today we will study IP addresses and how routers help traffic reach its destination.

Questions to ask first

  • Can two homes each have a laptop with 192.168.1.10?
  • Is a computer's IP address always permanent?

Live demonstration and teaching steps

  1. Draw two private networks, each containing a laptop labelled 192.168.1.10.
  2. Explain why the repeated private address does not create a global conflict.
  3. Run ipconfig in Windows and identify an IPv4 address and gateway.
  4. Discuss why a public service needs a reachable endpoint and appropriate network rules.

Code and commands

Windows Command Prompt
ipconfig

Classroom activity and instructor guidance

Follow a diagram of one packet sent from a home laptop through a local router and onward to a destination network. Emphasize that actual forwarding uses routes, not knowledge of a human-readable website name.

Review / exit questions

  • What is the difference between LAN and Internet?
  • Why can two private networks reuse the same IPv4 address?
  • What does a router do?
  • What is IPv6?
Homework / submission

Draw and label client, router, Internet and destination server. Do not publicly share sensitive network configuration.

90-minute flow

  1. 10 minOpening and review
  2. 20 minDNS and URLs
  3. 20 minHTTP and TLS
  4. 25 minTwo live demonstrations
  5. 15 minQuestions and homework

Essential concepts

Domain name
A human-friendly name such as example.com.
DNS
A distributed system that provides records, including IP addressing information.
URL
An address identifying a resource, including scheme, hostname and optional path.
HTTP
A protocol for requests and responses between web clients and servers.
HTTPS and TLS
HTTP carried over an encrypted TLS connection; it protects traffic in transit.
HTTP status codes
200 success, 301 redirect, 404 not found, 500 server error.

Instructor opening script

Yesterday we studied IP addresses. But when you open a website, do you usually type its numeric IP address?
No. You type a name such as example.com.
How does the computer learn where to send the request? DNS helps answer that question.
Today we follow the request from the browser address bar to the returned page.

Questions to ask first

  • Why are domain names useful?
  • What can HTTPS protect, and what can it not guarantee?

Live demonstration and teaching steps

  1. Run nslookup example.com to inspect a DNS lookup.
  2. Open https://example.com in a browser.
  3. Press F12 and open Developer Tools → Network; reload the page.
  4. Select the main document request and identify the URL, method, status and response headers.
  5. Explain the simplified stages: URL → DNS → connection/TLS → HTTP request/response → rendering.

Code and commands

Windows Command Prompt
nslookup example.com

Classroom activity and instructor guidance

Students draw six connected boxes: address entered, DNS lookup, connection established, TLS, HTTP exchange and browser render. Explain that caching or reused connections can change the real sequence.

Review / exit questions

  • What is DNS?
  • How is a URL different from a domain name?
  • What does status 404 mean?
  • Does HTTPS prove that an operator is trustworthy?
Homework / submission

Draw the lifecycle of a website request with at least six labelled steps.

What Is Cloud Computing? Introducing AWS

Learning objective: Connect local server and networking knowledge to cloud infrastructure, hosted services, AWS categories and cost considerations.

90-minute flow

  1. 15 minReview local server limitations
  2. 20 minWhat cloud computing provides
  3. 20 minExplore the AWS choices
  4. 20 minClassroom choice quiz
  5. 15 minCourse roadmap and homework

Essential concepts

Cloud computing
On-demand access to computing resources and managed services over a network.
Compute
Virtual servers, functions and containers that execute programs.
Storage
Services for retaining files, objects and other data.
Databases
Managed services for storing and querying structured data.
Networking
Addressing, routing, content delivery and controlling access to services.
Responsibility and cost
Cloud still uses physical infrastructure. Users must understand pricing, security settings and ongoing usage.

Instructor opening script

On our first day we created a website on an ordinary computer.
We then learned how clients and servers communicate, how networks and IP addresses work, and how a browser asks for a webpage.
But what if our server computer is switched off? What if thousands of users visit at once? What if we need more storage?
Cloud computing gives us ways to obtain computing, storage and managed services on demand. AWS is one platform that supplies them.

Questions to ask first

  • Does cloud computing eliminate physical computers?
  • Is hosting on AWS automatically free?
  • Who remains responsible for configuring access securely?

Live demonstration and teaching steps

  1. Show the AWS getting-started screen shared for this course.
  2. Discuss each option: Build with AI, Store files, Run a server, Build an API, Set up a database, Host a website, Automate deploys, Analyse data, Run containers and Just exploring.
  3. Ask students to choose the correct option for a static site, file storage, mobile backend, student database and Node.js server.
  4. Compare running a server on your laptop versus obtaining cloud compute on demand.
  5. Preview security and budget safeguards before any paid resource is provisioned.

Classroom activity and instructor guidance

Assign five scenarios to small groups. Each group picks an AWS starting option and justifies it. Stress that a starting option may lead to multiple possible AWS services.

Review / exit questions

  • What problem can cloud computing solve?
  • Is the cloud still physical hardware?
  • Name one cloud compute and one storage category.
  • Why must pricing and IAM be learned early?
Homework / submission
